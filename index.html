A Claude Code plugin · v5.1.1

Many sessions, one codebase, nothing trodden on.

Run several Claude Code sessions over one folder of projects. The toolkit gives them workspace-wide file locks, scans every edit for what a reviewer would catch, and holds the end of a turn until the change has actually passed its tests.

Why it exists

Parallel sessions are fast until they aren't.

Three things go wrong the moment more than one session works on the same tree — and all three are invisible until something is already broken.

01

They overwrite each other

Two sessions open the same file, both read it, both write it. The second write wins and the first one's work is gone with no error, no conflict and nothing in git to show it happened.

02

Standards drift per session

One session writes classes, the next writes functions. One builds a responsive UI, the next hard-codes 1920×1080. Nothing is wrong in isolation; the codebase ends up in two minds about everything.

03

"Done" is a claim, not a fact

A turn ends when the model stops talking, which is not the same as the change working. Tests that were never run and fixes whose cause was never found both end the turn exactly the same way.

What you get

Fifteen things that happen whether or not anyone remembers to ask.

Most of this is not a command you run. It is wired into the session's own lifecycle, so it applies to every session, every edit, every turn.

Workspace-wide file locks

A file is locked across every project under the workspace root before it is edited — not per project, not per session. Another live session holding it blocks you by name, so the collision becomes a message instead of a loss.

cli/locks.js

Every edit is scanned

opengrep, gitleaks, ShellCheck and ESLint run against the last commit after each edit to a code file. A new finding reaches the session once — pre-existing ones are counted, not repeated at every save.

cli/scan.js

A living map per project

A map of the codebase, a changelog with the what and the why, and a fix ledger — written per project and kept out of that project's git, so the records never land in a pull request.

<project>/.toolkit/

A Stop gate with teeth

The end of a turn is held, once, while an edited project has no passing test run since the change — or an unverified fix in its ledger. It checks every workspace the session edited in, dependents included.

hooks/stop-gate.js

UI rules nobody has to repeat

Every session that touches a UI is handed the same rules: adapt to the window actually given — size, aspect ratio, resolution, DPI, OS scale — hold shapes with aspect-ratio constraints, desktop first, and ship a mobile version too.

on by default

Design reviews by a panel

Five independent read-only judges score a built UI on layout, display resilience, usability, the mobile version and visual design. The designer answers every blocking issue, then it goes again.

up to 6 passes

Diagnosis before fixes

The fix ledger refuses to record a fix whose cause was never ruled in. A guess that happens to work is not a diagnosis, and the ledger will not let it pass as one.

tools/fix-ledger.js

Sourced research, in parallel

Read-only researcher subagents gather facts before the code is written. Every claim comes back with a URL, a file:line or captured command output — anything unsourced returns as an explicit unknown.

research-fanout

A scope contract first

Before a build that touches more than a file or two: the goal, what done means, the non-goals and a depth budget — written down, so going further than asked is checkable rather than a surprise.

scope-brief

Blast radius, once per file

The first time a file is edited in a session, the session is told who references it and which projects depend on it — before the change spreads, not after something downstream breaks.

cli/verify.js --refs

One paradigm, measured

Classes or functions is settled by reading the codebase rather than guessing: greenfield defaults to classes, an existing tree is matched, and the framework's own idiom beats the raw count.

code-paradigm

Screenshots at real sizes

Captures at the sizes a UI is genuinely opened at — monitors at 100%, 125% and 150% Windows scale, a 960-wide window, a phone and a tablet — so "it looks fine" is a measurement.

cli/capture.js

Nothing downloads quietly

Scanner installs show every file first — its source, size and SHA-256 — and fetch nothing until you say yes. Tools already on the machine are adopted rather than downloaded again.

cli/install.js

A verify command you approved

A project's test command runs only after you have approved its exact text on this machine, shown character for character and keyed by SHA-256. Change a character and it needs approving again; a non-printable or look-alike character cannot be approved at all.

cli/verify.js --trust

Mutation testing, where it is set up

Changed files can be mutation-tested with the Stryker installed in that project — never through npx, so nothing is fetched behind your back. Where a project has no Stryker it says so and passes, rather than failing on a tool you never chose.

tools/mutation-check.js

How it works

Wired into the session, not bolted onto your workflow.

There is no daemon, no service and nothing to remember. Each of these fires on a point in the session's own lifecycle.

Session start
You are given a label (A, B, …), the workspace and project you are in, any missing scanners, recent hook errors, settings that cannot be used — and the UI base rules.
UI work begins
The UI base rules and your own design preferences and recorded lessons are handed to the session, in any folder, workspace or not.
Before an edit
The file is locked workspace-wide. A live session holding it blocks you, by name. A protected_files entry is refused outright — for reading as well as writing.
After an edit
A changelog line in that file's project. For code: an async security scan against the last commit, including race patterns — a file checked then changed, a JSON state file written in place, a lock taken without exclusive create. A file's own eslint-disable or nosemgrep comment does not hide a finding.
Turn end
Held once if an edited project — or a dependent — has a verify command with no passing run since the change. Docs count; the project's own records do not. After two blocks on the same state it lets go.
A write outside the tools
A shell command that writes a file is recorded and reported at the next prompt — it was neither locked nor scanned. If it hit a file another session holds, you are told at once.
Session end
Every lock it held is released, in every workspace it edited in.

Design review

Five judges who never see each other's verdicts.

Ask for a review and the built UI is screenshotted at real sizes, then handed to five read-only judges in parallel. Each returns one JSON verdict. The designer answers every blocking issue, revises, and the round runs again.

LayoutAlignment, spacing, grid, hierarchy and consistency.
DisplayAspect ratios, resolutions, Windows scale and DPI.
UsabilityAccessibility, clarity, fidelity to your stated preferences.
MobileWhether the phone and tablet versions are genuinely usable.
VisualTypography, colour, component states, icons, restraint.
1–5 judges 12 passes per review, hard each judge once per pass a daily budget of judge runs read-only: they cannot edit

The limits live in code, not in a prompt — a session cannot talk its way past them.

Please read this before installing

This toolkit will increase your token usage.

Not as a side effect of a bug, and not by a little. It is the direct consequence of how the toolkit works: it adds context to sessions, re-checks what was done, and starts additional agents. Every one of those is a deliberate trade of tokens for quality, and you should know the trade before you take it.

Context is added to every session

Session start injects the workspace state and the UI rules. UI work injects the rules and your preferences again. That context is carried for the rest of the conversation.

Findings are delivered into the conversation

Each edit can return scanner findings, a changelog write and a blast-radius note. They are deduplicated, but they are still tokens on top of the edit itself.

The Stop gate can cost a whole extra turn

When a turn is held, the session runs the tests and responds — work that would not have happened at all without the gate.

Judges are subagents, and there are five

A full design review is up to five judges across up to six passes — as many as 30 agent runs, each reading the source and screenshots. This is by far the most expensive thing here.

Research fans out in parallel

research-fanout starts a read-only researcher per question. Each one browses and reads independently before reporting back.

Audits read whole codebases

/toolkit:audit-full is a careful three-pass read of one project's source. It is operator-triggered for exactly this reason.

What you can turn down

/toolkit:ui judges 2Fewer judges on a review. One to five; the cost is roughly linear.
/toolkit:ui passes 2Fewer rounds before a review has to settle.
/toolkit:ui auto-judge offJudges never run unasked — the default.
/toolkit:ui adaptive offStop injecting the UI base rules into UI work.
/toolkit:ui mobile offStop requiring a mobile version with every desktop UI.
code_globsNarrow what the scan covers, per project, in projects.md.

The expensive parts are opt-in by design: audits and reviews are operator-triggered, and judges do not run unless you ask. The always-on parts — locks, scanning, the changelog, the Stop gate — are the cheap ones.

In the folder that holds them: /toolkit:audit-workspace, then /toolkit:audit-full <project> for each one. Run /toolkit:setup if session start reports a missing scanner.

Straight answers

What it does not do.

A shell command that writes a file (cat, cp) is not seen by any hook. It is recorded and reported, but it was never locked and never scanned.
The scan covers the JavaScript and shell kinds of a project's code_globs. A file in another language is not scanned, and nothing says so at edit time.
The Stop gate is a reminder with teeth, not a lock. It holds a turn once; the session can end the turn on the next attempt.
The judges' cap counts agent starts. A judge already running can be sent a follow-up that no hook sees.
A folder outside the workspace cannot be registered as one of its projects — make it its own workspace.
5.1.x has not been run on Linux, and Claude Code itself has not been run there. The 5.0 suite was.
