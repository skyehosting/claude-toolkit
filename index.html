Overview

A plugin that lives inside Claude Code.

Install it once and it works inside every Claude Code session on your machine. It hooks into each step of a session, offers skills that Claude reaches for when the work calls for them, adds commands you can run, and brings read-only agents for research, review and judging.

It is built for developers who run more than one Claude Code session over a folder of projects, and for anyone who wants every session to follow the same standards without being told twice.

  • No server, no daemon, no telemetry: it runs where your sessions run
  • Node ≥ 22 built-ins only, no runtime dependencies
  • Windows 11 and Linux

What changes

Six things you notice on the first day.

Each session is capable on its own. Run several over one folder of projects and three things go wrong: they overwrite each other, every one starts from zero, and “done” is only a claim. This is what changes.

01

Parallel work stops costing you work

Locks and collision notices mean two sessions cannot silently overwrite each other's edits.

02

Security problems surface at the edit

New findings reach the session the moment they are written, not weeks later in a review.

03

“Done” means the tests passed

A turn that changed a project is held until its approved test command has passed since the change.

04

Every session knows the rules

The project map, your UI rules and your design preferences are handed over, so you stop repeating yourself.

05

Fixes are diagnosed, not guessed

A fix is recorded only after its cause was found with evidence, and closed only when the problem is really gone.

06

Interfaces that hold on every screen

UIs are built to adapt to any window, checked at real sizes and, when you ask, judged by a panel.

UI base rules

Built for every screen, without being told.

Every session that designs a user interface is handed the same nine rules, in any stack and any folder. They are on by default, and /toolkit:ui switches them.

Adapt to the window

  • Designed for the space the UI really gets: a 1080p monitor at 125% gives a page 1536×864.
  • Sizes, spacing and type scale together, with a readable minimum and maximum.
  • Small windows reflow on purpose: nothing overlaps, is cut off or scrolls sideways.

Hold every shape

  • Cards, panels, tiles and wide buttons keep their proportions with aspect-ratio constraints or maximum sizes.
  • Wide screens get margins or more columns, never stretched elements.
  • Images and video fit or crop; they never distort.

Desktop first, mobile too

  • A phone layout of the same UI is delivered with the desktop one: the same content, laid out for a thumb.
  • One column, touch targets of about 44 px, nothing that needs hover, no sideways scroll at 360 or 320 px.
  • The sizes it was checked at are named, never assumed.

Design review

Judged before you see it.

Ask for a design review and the built UI is screenshotted at real sizes, then handed to independent read-only judges. Each returns one verdict. The designer answers every blocking issue, revises, and the next pass begins.

judge 1 of 5

Layout

Alignment, spacing, grid, hierarchy and consistency.

judge 2 of 5

Display

Aspect ratios, resolutions, window sizes, Windows scale and DPI.

judge 3 of 5

Usability

Accessibility, clarity, and fidelity to your own preferences.

judge 4 of 5

Mobile

Whether the phone and tablet versions are genuinely easy to use.

judge 5 of 5

Visual

Typography, colour, states, icons, polish and restraint.

  1. Screenshots at real sizes
  2. Five verdicts, in parallel
  3. Every blocking issue answered: fixed, or declined with a reason
  4. The next pass checks the answers

A review ends when every judge passes, when a pass resolves nothing new, or at its cap; whatever is left comes to you.

Everything it does

33 features, in six groups.

Open a group to see each feature, when it acts and where it lives. “On its own” needs no command; “any folder” works outside a workspace too; “when you ask” is a skill, a command or an operator step.

Coordination

Several sessions, one folder of projects, no one stepping on anyone.

8 features

Workspace-wide file locks

Before every edit the file is locked across the whole workspace, every project in it. If another live session holds it, you are stopped and told which session. Locks are released when the session ends.

on its owncli/locks.js

Session labels and a board

Each session gets a label (A, B, …) at start, and .toolkit/board.md shows who holds which file.

on its own.toolkit/board.md

Writes outside the edit tools

A file changed by a shell command was neither locked nor scanned. The toolkit records it and tells the session at its next prompt; if another session holds that file, you are told at once.

on its owncli/scan.js --changed

Sessions from other folders

A session started elsewhere that edits inside the workspace is told the workspace's rules at its first edit, held by the same Stop gate, and has its locks released when it ends.

on its ownany session

Protected files

Files listed as protected in projects.md are refused to the Read, edit and Grep tools, and to the shell commands that name them (Bash, PowerShell, Monitor), for every session.

on its ownprotected_files

Projects in other folders

A project in a folder outside the workspace can be registered by its full path. It gets the same locks, scan and Stop gate, and keeps its records in its own .toolkit/ folder.

on its own/toolkit:audit-workspace

A file held by a stuck session

A blocked session is told who holds the file and when that session was last active. Once the holder has been inactive for 10 minutes, or its process is gone, you are shown a code such as unlock K7QF: type it in the waiting session within 30 minutes and the file is handed over. The toolkit never takes a file on its own.

when you askunlock CODE

Discord when a session waits on you

Off until you turn it on: a direct message from your own Discord bot, a channel post, or both, when a session asks you a question, has a plan for you to approve or waits on your prompt, and, if you choose, when it has finished its turn. You set it up in your own terminal, and its secrets file is refused to every tool.

when you ask/toolkit:notify

Quality gates

Checks that run whether or not anyone remembers to ask.

5 features

A security scan of every code edit

After each edit, gitleaks reads the file for secrets, and a code file gets the rules for its language, compared with the last commit: opengrep packs for JavaScript, TypeScript, C#, Python, PowerShell, Luau, shell and configuration files, ESLint's security rules on JavaScript, and ShellCheck on shell scripts. Only what the edit introduced is reported, once per session. A file's own suppression comments do not hide a finding.

on its ownhooks/security-scan.js

The Stop gate

A turn that changed a project is held once, until that project's test command, and its dependents', has passed since the edit, and until any fix in its ledger is re-verified. A strict project's gate holds it again at each attempt.

on its owncli/verify.js

Test commands you approved

A project's test command runs only after you approve its exact text on this machine, shown character for character and pinned by its SHA-256. Change a character and it needs approval again; a hidden or look-alike character can never be approved.

on its ownverify.js --trust

Blast radius

The first time a session edits a file, it is told which files reference it, which projects depend on it, and the exact commands that will check them.

on its ownverify.js --refs

Records for every project

A living map of the codebase, a changelog with a line per edit and the what and why of each change, a fix ledger and plans, in each project's .toolkit/ folder, kept out of its git.

on its own<project>/.toolkit/

Debugging discipline

Find the cause first. Prove the fix after.

5 features

Diagnosis before fixes

The fix ledger has a session list its hypotheses and rule them out with evidence it ran before it may record a fix. A test counts only once it failed against the unfixed code; a fix is closed when the problem is gone and nothing new appeared.

when you asktools/fix-ledger.js

A read-only security reviewer

The security-bug-auditor agent runs the scanners and a logic review of a change, reports what it finds, and re-checks a fix. It cannot edit anything.

when you askagent

Mutation testing

Changed files can be mutation-tested with the Stryker installed in the project, never fetched through npx. Without Stryker it says so and passes.

when you asktools/mutation-check.js

A panel of change reviewers

When you ask, five read-only reviewers (correctness, the callers of what changed, tests, security and structure) review the session's changes, for up to three passes. Every finding must quote its line and is checked by code before it counts; the session fixes it or declines it with a reason.

when you ask/toolkit:change-review

Security gap audits

A project is checked against the toolkit's security checklists for protections that are missing, not only for bad code. Every answer comes with its evidence.

when you ask/toolkit:audit-security

Interfaces

UIs that hold on every screen, in any folder, workspace or not.

6 features

UI base rules nobody has to repeat

Every session designing a UI is handed the same rules: adapt to the window it really gets (size, aspect ratio, resolution, DPI, Windows scale), hold shapes with aspect-ratio constraints, use the extra width of wide screens as margin, keep small windows working, and build desktop first with a mobile version too. On by default.

The rules, per stack

How each rule is done in CSS, Electron, WPF, WinForms, WinUI, Win32, Dear ImGui, Qt, Unity, Godot, Roblox and Unreal.

any folderdocs/ui-stacks.md

Your taste, remembered

Your design preferences and the lessons from your corrections travel with the rules, for every project or just one. A correction becomes a recorded lesson, so it is not repeated.

Directions before code

Two or three genuinely different design directions as standalone pages, to choose between before any production UI is written.

when you askcli/capture.js

A panel of judges

When you ask: up to five read-only judges (layout, display, usability, mobile, visual), one verdict each, for up to six passes. The designer answers every blocking issue with a fix or a reason. The limits are held in code.

Planning and research

Skills that fire when the work calls for them.

5 features

A scope brief first

For a build that touches more than a file or two: the goal, what done means, the non-goals and how deep to go, written down so that going further is checkable.

when you askscope-brief

Sourced research

Read-only researchers run in parallel. Every claim comes back with a URL, a file and line, or captured output; anything unsourced comes back as a named unknown.

when you askresearch-fanout

Code structure rules

Every session writing code is handed the same rules: match the code that exists, classes for new code with identity, state or a lifecycle, a framework's idiom at its boundary, small scripts plain. On by default.

One code paradigm

Classes or functions, decided by measuring the codebase: a new project defaults to classes, an existing one is matched, and a framework's own idiom wins.

Audits that build the map

Hand a session a newer zip and it updates the installed toolkit in place: it checks the installed version, backs the old folder up, swaps the new one in and refreshes Claude Code.

Before you install

It increases your token usage. On purpose.

It works by adding context to sessions, checking their work and starting extra agents. Each of those trades tokens for quality. Know the trade before you install.

Context at session start and for UI work

The workspace state at every session start, and in a project the code structure rules (about 2,200 characters); the UI base rules (about 3,500 characters) and your preferences when UI work begins.

every session
Notes after edits

Scan findings, the blast radius and notices. Each is delivered once, but it is added on top of the edit.

per edit
The Stop gate's extra turn

A held turn means the session runs the tests and answers again: work that would not have happened without the gate.

per changing turn
Subagents

Researchers run in parallel; the security reviewer reads the change.

when used
Design reviews

Up to 5 judges for up to 6 passes: as many as 30 agent runs, each reading screenshots and source. By far the largest cost.

only when you ask
Change reviews

Up to 5 reviewers for up to 3 passes: as many as 15 agent runs, each reading the change, within a daily budget of reviewer runs (45 by default).

only when you ask
Audits

A full audit reads a whole project in three passes; a security gap audit answers the checklists' controls with read-only auditors.

Install in four steps

  1. Unpack it where it will stayThe plugin runs from its folder in place, and Claude Code records the path.
  2. Install itAsk a Claude session to run these, or run them yourself:
    claude plugin marketplace add <folder>
claude plugin install toolkit@toolkit-local --scope user
  3. Restart Claude CodeNew hooks, skills and agents load when a session starts.
  4. Point it at your projectsIn the folder that holds them: /toolkit:audit-workspace, then /toolkit:audit-full <project>. /toolkit:setup installs any missing scanner, after your OK.

Already installed? Hand the new zip to a session and say “install this”. It finds the installed toolkit, checks the versions, backs the old folder up and updates it in place.

Questions

Straight answers.

How do I get access?

Choose Request access and fill in the short form on GitHub, signed in with the account you want to use. The request is a public issue in this page's repository, so leave out anything private. Each one is read by hand; once you are added, GitHub sends that account an invitation, and after you accept it the download link works. Access is free.

Does it help with just one session?

Yes. The scan, the Stop gate, the records, the fix ledger, the change reviews and the UI and code rules all work for a single session. The locks start to matter at two.

Do I need to set up a workspace?

For the locks, the scan, the changelog and the Stop gate, yes: /toolkit:audit-workspace sets one up in the folder that holds your projects. The UI rules, design options, screenshots and judges work in any folder.

Which languages does the scan cover?

Every edited text file is read for secrets by gitleaks. A file in a project's code_globs also gets the rules for its language: opengrep packs for JavaScript, TypeScript, C#, Python, PowerShell, Luau, shell and configuration files, ESLint on JavaScript and ShellCheck on shell scripts. workspace.js languages proposes the code_globs for the languages a project holds.

Does it send my code anywhere?

The toolkit runs on your machine, with no server and no telemetry, and its scanners run locally. Its only downloads are the scanners that /toolkit:setup installs after your OK. Discord notifications, off until you turn them on, send short texts to your own bot or webhook: a question and its options, the start of a plan, and, with done on, the start of Claude's final reply. What it adds to a session goes to Claude like the rest of the conversation.

Can I switch parts off, or remove it?

/toolkit:ui switches the UI rules and sets the judges and passes; /toolkit:code does the same for the code structure rules and the change reviewers; code_globs narrows the scan per project. claude plugin disable toolkit@toolkit-local turns it off, and claude plugin uninstall removes it.

Can I use it at work?

Yes. The licence allows any purpose, paid work included, except offering a product that competes with the toolkit.

Is it open source?

It is free and source-available. Anyone with access can read it, use it, change it and contribute to it, but nobody may sell it, sell a fork of it, or publish a rival copy, even a free one. That is narrower than open source in the strict sense, which by definition allows resale.

What it does not do

Protected files are guarded for the Read, edit and Grep tools and for the shell commands that name them. A tool that walks a folder by itself (grep -r, tar), git's history of a tracked file, a name made at run time, a script that opens the file, and MCP tools are not covered: keeping away from those stays a rule the session follows.

The scan advises; it never blocks. Its code scanners read the files in a project's code_globs; every other text file gets gitleaks alone.

The Stop gate holds a turn once; the session can end it at the next attempt. A strict project's gate holds it at each attempt, within a bound. Esc always ends a turn.

The judges' and reviewers' caps count agent starts. A message sent to a running one is refused; what you type to it yourself is not counted.

An unlock code is meant for you alone, but a session that reads its transcript could type it. A code only moves a file whose holder is still stuck or gone, and every hand-over is announced.

A project in another folder belongs to one workspace at a time, and a network (UNC) path cannot be registered.

Built and tested on Windows 11. The 5.2.2 suite was run on Ubuntu 24.04, and 5.3.0 fixes what that run found; 5.3.1 itself has not been run on Linux yet.
